# 手机 Agent 能力对标（Mika Parity）— 战略设计

## 1. Problem

本仓库已有一个可运行的 Android 原生 Agent（`local.termux.agentbridge`），核心是「模型循环 + 无障碍执行」，但能力广度明显落后于同赛道的开源项目 Mika：

- 只有单会话、单线程执行，任务进行中无法并行处理另一件事。
- 只有无障碍控件与可选的云端视觉，没有内置 OCR，自绘界面/无标签控件基本不可用。
- 没有长期记忆、没有定时/条件任务、没有内置浏览器、没有 Linux 沙箱。
- 只能从 App 内发起任务，没有系统分享入口，也不能被电脑端 CLI/MCP 调用。
- 执行过程缺少统一的审计与恢复机制，进程被杀后无法交代。

这导致产品在「能办成多少种事」上被 Mika 全面压制。本设计的目标不是像素级复制 Mika，而是**对齐能力基线，同时保留并强化自身在可信执行上的差异**。

## 2. Vision

在 Android 上提供一个**能力接近 Mika、但执行过程可授权、可审计、可回滚**的个人 Agent：

- 用户一句话交代任务，Agent 在手机上把事办成，不占用主屏。
- 每一次对外动作都有记录、有边界、有停止手段。
- 用户对「它记住了什么、看了什么、发出去了什么」始终有完全可见性与删除权。

一句话定位：**Mika 的能力广度 + 可问责的执行层。**

## 3. Intent Contract

```
intent: 在不放弃可信执行优势的前提下，分阶段把 Android Agent 的能力广度对齐 Mika。
constraints:
  - 不破坏现有 APK 包名 local.termux.agentbridge 与签名，保持可覆盖升级。
  - 不提交任何密钥、聊天导出、用户数据到仓库。
  - 不做后台静默画像；长期记忆只来自用户显式表达并经过确认。
  - 屏幕内容上传模型必须可关闭、可脱敏，并保留现有审批策略。
  - 现有 build.py / Java 技术栈默认保留；迁移构建体系需单独立项。
  - 每个阶段都必须有可运行的回归验证，不以编译通过代替真机验证。
success_criteria:
  - 能力清单中 Phase 1–4 的退出标准全部达成。
  - 每阶段任务成功率、人工接管次数、审计覆盖率可量化并留存记录。
  - 现有 1.2.0 的审批、视觉补盲与迁移能力不回退。
risk_level: high
```

## 4. Verification Contract

```
verify_steps:
  - 编译：python3 android-app/build.py --tools <build-tools> --android <android.jar>
  - 单测：android-app/tests 下 Java 测试（PolicyTest、EfficiencyTest）按现有 runner 执行
  - 策略回归：敏感动作、白名单外 App、视觉点击越界必须被拒绝，并写入审计
  - 恢复验证：任务执行中杀进程，重启后必须给出中断交代，且不重复执行已完成步骤
  - 记忆验证：新增/修改/删除记忆后，上下文与界面同步，删除后不可再被模型读到
  - 并行验证：两个任务同时执行时互不干扰，同 App 冲突按队列等待且不死锁
  - 真机矩阵：至少覆盖 Android 12、14 各一台设备，记录执行录屏与结果
confirm:
  - 每阶段结束时产出一份 VALIDATION 追加记录，包含设备、场景、成功率与已知失败。
```

## 5. Governance Contract

```
approval_gates:
  - 阶段设计评审：每个 Phase 开始前单独 brainstorm + writing-plans，经人工批准。
  - 高风险变更：新增系统权限、虚拟屏/无线调试、沙箱、外部网络入口，必须人工 gate。
  - 数据模型变更：SQLite 迁移脚本必须先备份、后迁移，且可回滚。
  - 发布：每个 Phase 产出可安装 APK，人工真机验收后才允许合并。
rollback:
  - 所有新能力由 feature flag 控制，默认关闭，可单独关闭而不回滚版本。
  - 数据库迁移只增不删；失败时恢复到迁移前备份。
  - 保留现有签名与安装包，出现问题时回退到上一个可用 APK。
ownership: 仓库维护者（snsnnd）负责阶段验收与发布决策。
```

## 6. Non-goals

- **不做后台静默读取与隐式画像**。这不是能力差距，而是合规与信任红线。
- **不复刻 Mika 的宽松审批默认值**（只确认花钱的操作）。本项目保留并按任务收紧授权。
- **不追求 UI 像素级一致**。只对齐任务闭环与关键交互。
- **不在本 initiative 内迁移到 Kotlin/Gradle**，除非某阶段被证明强依赖。
- **不内嵌完整 Termux 工具链**；Linux 沙箱单独做 go/no-go。
- **不承诺「操作所有 App」**，也不做绕过风控、批量骚扰类自动化。

## 7. Stakeholders

| 角色 | 关心什么 |
|---|---|
| 维护者 | 改动可控、可验证、不引入不可维护的运行时 |
| 终端用户 | 任务成功率、是否打扰主屏、隐私与可撤销 |
| 开发者/企业调用方 | 能否通过 CLI/MCP 接入、审计与私有化 |
| 平台审核方 | 无障碍用途是否合规、是否滥用系统能力 |

## 8. 现状与差距

| 能力 | 当前实现 | Mika | 目标阶段 | 难度 |
|---|---|---|---|---|
| 执行循环 | `AgentService` 单线程、最多 20 轮、单会话 | 任务中心 + 多 Run | P1 | 中 |
| 并发 | 无 | 多对话并行、同 App 排队、死锁检测 | P3 | 中高 |
| 感知 | 无障碍节点 + `ObservationCodec` 精简 | 无障碍 + 内置 OCR + 视觉 | P2 | 中 |
| 视觉 | `VisualSession` 单次截图、逐次确认 | 可选视觉补盲 | 已有，P2 增强 | 低 |
| 记忆 | SQLite 会话摘要 | 长期记忆（查/改/删）+ 技能知识 | P2 | 中低 |
| 浏览器 | 无 | 内置桌面版浏览器、登录保持 | P3 | 中 |
| 沙箱 | App UID `sh` | arm64 Linux 沙箱 | P5 | 高 |
| 定时/条件 | 无 | 定时、条件比较、暂停修改 | P3 | 中 |
| 外部入口 | 仅 App 内 | 分享、悬浮胶囊、CLI、MCP、飞书 | P2/P4 | 中 |
| 审计/恢复 | 尽力识别 + 通知审批 | 较弱 | P1 | 中 |
| 构建 | `build.py` 直编 Java | Gradle + Kotlin 双模块 | 不在本 initiative | — |

## 9. 目标架构

分层保持简单，避免一次性重写：

```text
入口层：App 对话 / 系统分享 / 定时触发 / CLI·MCP（后续）
                    │
任务层：TaskCenter —— 多 Run 注册、队列、并行上限、同 App 锁、恢复
                    │
循环层：AgentLoop —— 上下文构建、模型调用、工具分发、停止规则
                    │
策略层：Policy & Audit —— 能力白名单、敏感动作确认、逐步审计、停止总结
                    │
能力层：phone(无障碍/虚拟屏) / vision+ocr / browser / files+shell / memory / scheduler
                    │
存储层：SQLite（会话/消息/记忆/Run/审计）+ Keystore（密钥）
```

关键原则：

- **循环层不认识具体能力**，只通过能力提供者接口调度；便于后续替换引擎或加能力。
- **所有对外动作必须经过策略层**，审计与确认不能被能力实现绕过。
- **任务状态持久化**，进程重启后能交代、能续跑、不重复副作用。
- **能力按 feature flag 装配**，未启用的能力不注册工具、不申请权限。

## 10. 阶段拆分

### Phase 1：可信执行与任务中心骨架（风险：中高）

- 引入 `TaskCenter`/`Run` 抽象，即使暂时串行也走统一任务模型。
- 每任务能力白名单：仅注册任务需要的工具，App 级 allowlist。
- 审计日志：每次工具调用记录动作、目标、结果、是否越权；只存脱敏摘要。
- 停止总结：停止后交代做了什么、外发几次、哪些没做完。
- 进程重启恢复：标记中断、补告、不重复已完成步骤。

**退出标准**：100% 工具调用有审计记录；越权动作无法执行；杀进程后能正确交代且无重复副作用。

### Phase 2：感知、记忆与分享入口（风险：中）

- 打包离线 OCR（方案在计划阶段定：ML Kit / PaddleOCR 轻量模型 / 其他），无控件界面可用。
- 观测编码增强：场景复用、过期上下文裁剪、动作后回传新 UI（在 1.2 基础上补齐）。
- 长期记忆：显式事实/偏好/习惯，习惯类需批准；提供查看、修改、删除、导出；Keystore 加密。
- 系统分享入口：接收文本/链接/文件并创建任务，带来源标记。

**退出标准**：自绘界面任务可完成；记忆可查改删且删除后不再进入上下文；分享可创建任务。

### Phase 3：并行、调度与浏览器（风险：中）

- 多对话并行执行，同 App 互斥、等待上限、死锁识别。
- 定时与条件任务：到点执行、条件比较、暂停/修改/立即执行。
- 内置浏览器：WebView、桌面 UA、登录保持、下载/上传、翻页节奏保护。
- 通知内审批与悬浮入口（可裁剪，不做成必选）。

**退出标准**：双任务并行互不干扰；定时任务可靠触发；浏览器任务闭环跑通。

### Phase 4：后台屏与外部接入（风险：高，先验证后承诺）

- 技术验证（spike）：无线调试 helper / shell UID / 虚拟显示 / 输入注入的可行性与合规性。
- 可行则实现后台屏执行；不可行则降级为「最小干扰前台执行」并记录否决理由。
- CLI/MCP 入口：USB 与局域网，令牌鉴权，外部只能派任务与取结果，付款确认仍在手机。

**退出标准**：后台屏跑通至少一个真实闭环，或产出明确的技术否决报告；外部入口可用且不能绕过策略层。

### Phase 5：Linux 沙箱（风险：高，go/no-go）

- arm64 proot 方案、默认断网、按会话工作区、体积与性能评估。
- 若体积/安全/维护成本不可接受，明确记录不做，不留半成品。

**退出标准**：沙箱可运行 Python/Node 基础任务，默认无网络，卸载可清理，体积在可接受范围。

## 11. 验证与度量

每个 Phase 记录以下指标（不含消息正文）：

- 任务成功率、每任务人工接管次数、失败恢复率。
- 审计覆盖率（有完整记录的对外动作占比）、越权/误操作次数。
- 单任务模型调用次数与 Token 成本。
- APK 体积变化、冷启动与观察延迟。

## 12. Risks & Open Questions

| 风险 | 影响 | 应对 |
|---|---|---|
| 虚拟屏 / 无线调试方案不可行或违反商店政策 | P4 无法交付 | 先 spike，允许否决；保留降级路径 |
| 无障碍 API 用途审核 | 应用被拒审/下架 | 权限说明如实描述，避免通用自动化宣传 |
| 屏幕内容上传第三方模型 | 隐私与合规风险 | 默认脱敏、可关闭、优先本地/境内模型 |
| OCR/沙箱导致 APK 膨胀 | 分发与安装体验 | 按 ABI 拆包、模型按需下载、P5 设门槛 |
| 构建体系（无 Gradle）限制大型改造 | 开发效率 | 每阶段评估；必要时单独立项迁移 |
| 追平式开发维护成本 | 长期不可持续 | 只对齐闭环，不追功能清单；优先复用成熟组件 |
| Mika 快速迭代 | 永远落后 | 以自身可信执行 + 垂直场景为差异，不逐版本对标 |

**Open Questions（需在计划阶段定）**

1. 目标用户优先个人还是企业/开发者？这决定 P3 之后优先级。
2. OCR 采用系统/云服务还是完全离线模型？涉及 APK 体积与隐私。
3. 是否在 P1 同时清理仓库历史中的密钥与 `.uploads` 聊天导出？
4. 虚拟屏是否属于「必须」，还是可用「不抢焦点」方案替代？
5. 是否接受为 P4 引入无线调试依赖（用户设置成本）？

## 13. 决策记录

| # | 决策 | 选择 | 放弃的替代方案 |
|---|---|---|---|
| 1 | 技术栈 | 保留 Java + `build.py` | 重写为 Kotlin/Gradle |
| 2 | 复刻方式 | 能力基线对齐，不做像素级复制 | 全功能照搬 |
| 3 | 差异化 | 可信执行、审计、可撤销 | 拼功能数量 |
| 4 | 记忆形态 | 显式、可查改删、本地加密 | 后台隐式画像 |
| 5 | 虚拟屏 | 先 spike 再承诺 | 直接按 Mika 方案实现 |
| 6 | 沙箱 | 独立 go/no-go | 默认纳入主线 |
